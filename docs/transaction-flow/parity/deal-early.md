## Summary (10 lines)

1. **Stage 10 (reaffirmation / vehicle hold / condition disclosure / material change) does not exist anywhere in code.** A wide search for `reaffirm|reaffirmation|hold_until|holdUntil|vehicle_hold|deal_recap|dealRecap|worksheet|material.?change|condition.?disclosure|acknowledg` across `app/ lib/ components/ prisma/ scripts/` returns only marketing copy (dealer-fee calculator, lead magnets, SEO text) and unrelated acknowledgments (affiliate compliance, e-sign consent). `DealStatus` (schema.prisma:1513-1530) has no `DEALER_CONFIRMATION`/`RECAP_PENDING`; every Deal is minted directly at `FINANCING_PENDING` by all three creation paths (`lib/services/deal/select-offer.service.ts:53-55`, `app/api/buyer/requests/[requestId]/offer/respond/route.ts:81-86`, `app/api/admin/deals/route.ts:50-52`).
2. **Stage 11 (final deal recap) does not exist.** No `deal_recaps` model, no versioned recap, no optional-product acceptance, no dual confirmation. Contract Shield only pattern-matches add-ons (`lib/services/contract-shield/contract-shield.service.ts:31-110`) and cannot compare a contract against a recap that was never captured.
3. **The identity firewall lifts at award (Stage 9), not at reaffirmation.** `lib/services/notifications/dealer-award.ts:132-148` sends first name + last initial to the winner; `lib/services/dealer/dealer-deals.service.ts:111-121,154-164` returns full name/email/phone/city/state/zip for any owned Deal; `app/dealer/deals/[dealId]/page.tsx:40` shows contact whenever `status !== "PENDING"`, i.e. immediately at `FINANCING_PENDING`. Pre-award anonymization is correct (`app/api/dealer/auctions/[auctionId]/route.ts:10-11,78,113`).
4. **Outside-winner onboarding is BUILT as parts but NOT sequenced on the Deal.** Claim tokens (`lib/services/dealer-recruitment/account-claim.service.ts`), prospect claim (`prospect-claim.service.ts`), license verification (`lib/services/dealer/dealer-verification.service.ts:37-113`), agreement/verification state (`:126-137`) all exist; nothing in `canTransition` (`deal.service.ts:15-70`) or the award dispatch checks them. The award email for a placeholder dealer links to `/dealer/deals/{dealId}` which an unregistered dealer cannot open (`dealer-award.ts:137,246`). The verification gate is a DB feature flag, default OFF (`dealer-auction-eligibility.service.ts:20-21,53`).
5. **Financing is a single stage that the buyer self-advances past.** `POST /api/buyer/financing` (`app/api/buyer/financing/route.ts:64-92`) and `PATCH /api/buyer/deal/financing` (`app/api/buyer/deal/financing/route.ts:19-28`) both advance `FINANCING_PENDING → FEE_PENDING` on the buyer's word (`actorRole: "BUYER"`). There is no terms-locked checkpoint, no completed checkpoint, and `COMPLETED` is gated only on insurance (`deal.service.ts:134-138`) — the owner's rule "never complete without financing COMPLETED/NOT_REQUIRED_CASH and funding cleared" is unmet.
6. **`FinancingStatus` is `PENDING|SELECTED|APPROVED|DECLINED`** (schema.prisma:1711-1716). Writers: buyer → `SELECTED` (`app/api/buyer/financing/route.ts:73,81`); system orchestrator → `APPROVED` (`financing-orchestrator.service.ts:107-127`, which has **zero production callers**); `DECLINED` is never written; no admin route writes `Financing`. `Financing` lacks every spec-added field (schema.prisma:2059-2073). No exhaustive TS switch exists — consumers are string-keyed maps (`FinancingPreApprovalClient.tsx:64-73`, `app/dealer/financing/page.tsx:12-18`).
7. **`credit_applications` is NOT frozen — it is live on the buyer transaction route.** `POST /api/buyer/financing/apply` (`app/api/buyer/financing/apply/route.ts:17,81-97`) accepts an SSN, income, employment and DOB from an authenticated buyer for a deal at `FINANCING_PENDING` and writes a `credit_applications` row (encrypted). `app/buyer/financing/page.tsx:40-44` reads it. The admin review queue (`/api/admin/financing-reviews/**`, `/admin/financing-reviews`, `/admin/manual-reviews`) reads and advances it. The only UI mitigation is that the buyer page no longer renders the form (`page.tsx:88-108`); the API remains callable. This directly contradicts §2 "Collects a Social Security number anywhere in the buy transaction — never" and §12.
8. **External pre-approval evidence is BUILT and reviewer-gated but attaches to the buyer/prequal, not the Deal.** `ExternalPreApproval` (schema.prisma:2015-2034) carries lender/amount/APR/term/expiry/documentUrl/reviewedAt/reviewedBy; approval requires `finance.preapproval.decide` (`lib/auth/permissions.ts:83`), a ≥10-char reason and an explicit OFAC attestation (`app/api/admin/external-preapprovals/[id]/approve/route.ts:20-28,53-67`), and writes `PreQualification` (`:77-108`) — never `Financing`. No `deal_id`. `ExternalPreApprovalDocument` (schema.prisma:3322-3331) has zero code references.
9. **Strong safeguards to preserve:** the guarded CAS deal seam (`deal.service.ts:104-216`), the tamper-evident append-only financing audit chain with DB triggers (`financing-audit.service.ts`, migration `20261004000000`), the fail-closed compliance-rule layer, the OFAC attestation on external approvals, the server-side prequal OTD ceiling on both buyer financing routes, the buyer 24h financing nudge (`nudge.service.ts:71-79`), the `no-inhouse-financing-on-auction-spine` executable guard, and the encrypted-at-rest / fail-closed-without-key handling on the (to-be-retired) apply route.
10. **Required work, in order:** (a) freeze `credit_applications` by removing the apply route + page read + review-queue wiring and extending the existing spine guard test to the whole transaction route tree; (b) extend `FinancingStatus`/`Financing`/`ExternalPreApproval(deal_id)` and add the terms-locked and completed checkpoints as `canTransition` guards; (c) add `DEALER_CONFIRMATION`/`RECAP_PENDING` DealStatus values, `dealer_reaffirmations` and `deal_recaps` models, the 12h/24h reaffirmation reminder cron, hold-until on Deal, and sequence outside-winner claim/verification/agreement before advancement; (d) move the identity-firewall lift from award dispatch to reaffirmation.
