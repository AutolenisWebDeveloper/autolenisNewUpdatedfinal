## Summary (10 lines)

1. The background substrate is **Vercel Cron → `withCronRun` (CronJobLog) → service**, authenticated fail-closed by `lib/security/cron-auth.ts` (constant-time `Bearer <CRON_SECRET>`, 500 when unset) and again at the edge in `proxy.ts:323`. 67 routes are scheduled in `vercel.json`; `lib/services/monitoring/cron-schedule.ts` mirrors it and a test pins both directions. Dead-cron and failing-cron detectors (`dead-cron.service.ts`) alert via SYSTEM_ALERT Notification + `notifyOncall`.
2. **Inngest is removed from code** (no `lib/inngest`, no `app/api/inngest`, no package dep) — residue is env/doc/schema-column only. **QStash is NOT removed from code**: `@upstash/qstash` dep, `lib/qstash/*`, 16 `app/api/jobs/*` routes and four live producers remain, while commit f23b361 asserts the QStash service "no longer exists". Every flag-OFF lifecycle workload (auction_active, dealer_invited, offer_received, deal_complete, form_submitted) and the voice/affiliate producers therefore dispatch into a dead vendor → swallowed → `jobs_dead_letter` row → terminalized by `dlq-drain`. **BROKEN.**
3. The canonical claiming patterns the new `queue_items` writer and `comms_outbox` dispatcher must reuse: (a) `lib/jobs/idempotency.ts` `claimJob` (idempotency_keys insert + stale/failed reclaim CAS on created_at) for per-entity leases; (b) marker-column CAS via `prisma.*.updateMany({where:{marker:null}})` (auction `postCloseProcessedAt`, deal `dealerAwardDispatchedAt`, `allowedPredecessors("PAID")`); (c) Supabase status CAS `pending→sending` + `claimed_at` stale reclaim (`comms-outbox.service.ts:329-355`, identical in lifecycle/lead-nurture/outreach/refinance drains). No SQL claiming function / `FOR UPDATE SKIP LOCKED` exists anywhere (searched `migrations/`, `prisma/`, `lib/`).
4. `comms_outbox` exists only as raw Supabase SQL (`prisma/manual_supabase_sql/comms_outbox.sql`), not a Prisma model, so it cannot participate in a `prisma.$transaction` (spec §20 atomic completion, §27) — a schema move is a prerequisite. Its drain has CAS claim, bounded retry (4), crash-uncertain no-resend, but **no terminal-failure Operations alert** (logger.error only), no trigger/state recheck, no cancellation rule.
5. Only 5 of ~75 `resend.service.ts` senders route through the outbox (`enqueueTransactionalEmail`); 71 still call `sendIdempotent` (direct Resend). Lifecycle touches send through a third rail (`lib/qstash/notify.ts`). Four send rails coexist → DUPLICATED.
